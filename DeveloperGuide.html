    Design

    Architecture

    The Architecture Diagram given above explains the high-level design of the App.

    The following provides a quick overview of the main components and their interactions.

    Main components of the architecture

    Main (consisting of classes Main and MainApp) is in charge of the app launch and shut down.

    • At app launch, it initializes the other components in the correct sequence, and connects them up with each other.
    • At shut down, it shuts down the other components and invokes cleanup methods where necessary.

    The bulk of the app's work is done by the following four components:

    • UI: The UI of the App.
    • Logic: The command executor.
    • Model: Holds the data of the App in memory.
    • Storage: Reads data from, and writes data to, the hard disk.

    Commons represents a collection of classes used by multiple other components.

    How the architecture components interact with each other

    The sequence diagram below follows a successful delete 1 across the main components. The ref frame summarizes parsing and execution on a detached model; delete execution is expanded separately.

    updatedRoster means stagedModel.getRoster(), and predicate means stagedModel.getPersonListPredicate(). Preparing the staged model copies the live roster, preferences, filter, and sort comparator; those accessor calls are omitted. A snapshot of the displayed positions breaks comparator ties in the detached copy, preserving the athlete addressed by each displayed index after consecutive sorts. This tie breaker is not installed in the live model and does not reorder saved records. After saving and updating the live model, withDataSaved() creates savedResult; its call is omitted. The live sort comparator is retained. JavaFX observes the published change, and MainWindow displays the result.

    The separate failure trace shows what happens if saving throws an IOException, including an AccessDeniedException. LogicManager wraps it in CommandException before MainWindow displays the error. No staged change is published to the live model.

    Both traces assume valid input and a valid displayed index. Unlabelled dashed replies return control from void methods or constructors; exception replies show propagation rather than a normal return value.

    Each of the four main components (also shown in the diagram above),

    • defines its API in an interface with the same name as the Component.
    • provides its functionality through a concrete {Component Name}Manager class that implements the corresponding API interface.

    For example, the Logic component defines its API in Logic.java and implements it in LogicManager.java. Other components interact with a component through its interface rather than its concrete class, preventing them from coupling to that component's implementation, as illustrated in the following partial class diagram.

    The sections below give more details of each component.

    UI component

    The API of this component is specified in Ui.java

    The UI consists of a MainWindow and its parts, such as CommandBox, ResultDisplay, PersonListPanel, and StatusBarFooter. All of these, including MainWindow, inherit from the abstract UiPart class, which captures common behavior among classes that represent visible GUI parts.

    MainWindow eagerly creates one HelpWindow. Its fillInnerParts() method creates the remaining parts; CommandBox is attached to the scene graph without a direct MainWindow field. CommandBox owns an AutocompleteEngine, and each PersonCard holds the Person it displays. Generic JavaFX root parameters and toolkit details are omitted from this partial view.

    The UI component uses the JavaFX UI framework. The layouts of these UI parts are defined in matching .fxml files in src/main/resources/view. For example, MainWindow.fxml specifies the layout of MainWindow.

    MainWindow reads the saved window bounds from GuiSettings and uses the static WindowPlacement.fit helper to fit those outer bounds, including decorations, inside the visual bounds of a connected screen. A reachable saved position selects the screen with the largest overlap; an unreachable position falls back to the primary screen's center. Both restoration paths cap dimensions and clamp coordinates. The preferred minimum is 450 by 400 pixels, limited by the selected screen's usable area. Normal bounds are remembered in preferences in memory as the window moves or resizes, allowing normal bounds to survive maximized, minimized, full-screen and OS quit paths. Preference storage writes them on shutdown. The roster can shrink and scroll independently of the input and footer; command execution does not resize the stage. HelpWindow uses the same fitting helper with its own 480 by 320 minimum, starts on its owner's screen, and retains later user placement within the session.

    The UI component,

    • executes user commands using the Logic component.
    • listens for changes to Model data so that the UI can be updated with the modified data.
    • keeps a reference to the Logic component, because the UI relies on the Logic to execute commands.
    • depends on some classes in the Model component because it displays Person objects from the model.

    Logic component

    API : Logic.java

    Here's a (partial) class diagram of the Logic component:

    LogicManager implements Logic, owns its TrackFlowParser, and holds references to the live Model and Storage. Commands return a CommandResult; LogicManager calls withDataSaved() only after saving a roster change successfully.     The delete trace focuses on the command's work. Parsing has already created DeleteCommand, and LogicManager has prepared a detached model with the current roster and display state.     How the Logic component works:

    1. When Logic is called upon to execute a command, LogicManager passes its text to TrackFlowParser. Parameterized commands are delegated to a dedicated parser (e.g., DeleteCommandParser); clear, help, and exit are validated and constructed directly by TrackFlowParser.
    2. This results in a Command object (more precisely, an object of one of its subclasses e.g., DeleteCommand) which is executed by the LogicManager.
    3. The command can communicate with the Model when it is executed (e.g. to delete a person).
      Note that although this is shown as a single step in the diagram above for simplicity, the code can require several interactions between the command object and the Model to complete the operation.
    4. A roster-changing command identifies itself through Command.changesRoster(). LogicManager executes it against a detached model containing the current roster, filter, and sort order. It saves the staged roster before publishing the change to the live model. If saving fails, the live roster and displayed list are never changed. View-only commands such as list, find, filter, sort, help, and exit execute directly and do not write the roster.
    5. The result of the command execution is encapsulated as a CommandResult object which is returned from Logic.

    The following partial class diagram expands the parsing helpers, using the concrete EditCommandParser as an example. The other dedicated parsers, including the shared tag/untag parser hierarchy, are omitted for clarity.

    How the parsing works:

    • TrackFlowParser recognizes command words without considering letter case. For parameterized commands such as edit, it creates the dedicated parser and returns the resulting command. The no-argument commands clear, help, and exit are validated and constructed directly instead.
    • EditCommandParser implements Parser<EditCommand>. It uses prefix constants from CliSyntax, calls ParserUtil.verifyNoUnknownPrefixes, and tokenizes arguments through ArgumentTokenizer.
    • ArgumentTokenizer recognizes supported prefixes at whitespace boundaries without considering letter case. Escaped prefix-like text stays within a value, and exactly one extra slash is removed after arguments are split.
    • ArgumentMultimap retains every supplied value for a prefix. EditCommandParser validates the index, rejects duplicate supported prefixes, parses the supplied fields, and requires at least one field before constructing an EditCommand. Parser and field-validation failures are reported as ParseException.

    Model component

    API : Model.java

    The Model component,

    • stores the athlete roster data i.e., all Person objects (which are contained in a UniquePersonList object).
    • stores the Person objects selected by the current filter, such as search results, in a FilteredList, and wraps that view in a SortedList for display ordering. It exposes the sorted view as an ObservableList<Person> that the UI can observe and bind to, so the UI updates when filtering, sorting, or roster data changes.
    • retains the active Predicate<Person> and optional Comparator<Person> separately as display state. Changing either updates the corresponding JavaFX view without changing the stored roster order.
    • distinguishes duplicate identity from complete value equality. Person.isSamePerson compares the normalized name and matching contact details, while Person.equals and hashCode include every stored field, including the remark.
    • stores a UserPrefs object that represents the user’s preferences (currently, just the GUI settings). This is exposed to the outside as a ReadOnlyUserPrefs object.
    • does not depend on any of the other three components (as the Model represents data entities of the domain, they should make sense on their own without depending on other components)

    The following diagram focuses on stored athlete fields. Each Tag is one track event of the athlete (e.g. 100m); see Event tagging. UniqueTagList is not part of the implementation. AthleteRoster implements ReadOnlyRoster, exposing its athletes through an unmodifiable ObservableList<Person>. It owns one UniquePersonList, which retains athletes in list order and enforces uniqueness using Person.isSamePerson. The diagram omits the intermediate JavaFX collection classes.

    The value-field links are ordinary associations: immutable value objects can be shared between different Person instances, such as during an edit. Person copies its tag set, while the individual immutable Tag objects may be shared. The tag association is an unordered set: equality ignores case, so differently cased spellings represent the same event, while display retains the stored spelling.

    Storage component

    API : Storage.java

    This partial view shows the storage adapters and DTOs; model conversion and file utilities are omitted. The stored JSON roster property remains persons so that existing roster files continue to load.

    The Storage component,

    • can save both athlete roster data and user preference data in JSON format, and read them back into corresponding objects.
    • is implemented by StorageManager, which delegates the actual JSON file access to JsonRosterStorage and JsonUserPrefsStorage (one class per data file).
    • writes JSON to a temporary sibling file before replacing the destination. FileUtil uses an atomic move when the filesystem supports it and cleans up the temporary file after success or failure.
    • depends on some classes in the Model component (because the Storage component's job is to save/retrieve objects that belong to the Model)

    Roster JSON mapping

    The following partial class diagram expands the storage overview's model conversion dependencies. JsonSerializableRoster retains a list of JsonAdaptedPerson, each of which retains a list of JsonAdaptedTag. These are ordinary navigable associations; the adapters do not retain model objects. The JSON roster key remains persons for compatibility with existing files.

    On saving, JsonRosterStorage constructs JsonSerializableRoster from a ReadOnlyRoster. Its constructor maps each Person to a JsonAdaptedPerson, which maps the model's Set<Tag> to a List<JsonAdaptedTag>. JsonAdaptedTag serializes as a tag-name string, so the persisted tags array contains strings. The model tag set has no ordering guarantee.

    On loading, Jackson reconstructs the adapters and toModelType() validates stored values before creating Tag and Person objects and adding them to a new AthleteRoster, which implements ReadOnlyRoster. Tag conversion checks tag names; person conversion checks required fields and the constraints on name, age category, phone, email and address. A missing age category defaults to Open, and missing or null tags become an empty list. The JSON tag list becomes a HashSet<Tag>: repeated tags, including case variants, collapse according to Tag.equals and hashCode.

    A missing or null persons list, null athlete/tag entries, invalid field values, and duplicate athletes (according to Person.isSamePerson) cause IllegalValueException; JsonRosterStorage wraps it in DataLoadingException. File-reading or JSON-decoding failures, including a JSON null root, also produce DataLoadingException through JsonUtil. An absent file instead returns Optional.empty().

    Implementation

    This section describes some noteworthy details on how certain features are implemented.

    Command parsing and validation

    TrackFlowParser treats command words without considering letter case and routes commands with parameters to their dedicated parsers. Its initial matcher accepts line breaks in arguments; the entire submission is still parsed as one command, not a batch. Each field keeps its existing validation rules. The JavaFX command box is a single-line TextField that removes pasted tabs and line breaks before parsing; users should paste commands on one line with spaces. Parser-level tests exercise multiline input directly.

    CommandWhitespace defines syntax separators as characters accepted by Character.isWhitespace or Character.isSpaceChar, including non-breaking, figure, narrow non-breaking, and em spaces. Command-word splitting, no-argument validation, index boundaries, broad search keywords, and sort arguments share this rule. Only boundary whitespace is stripped; whitespace inside field values retains its existing validation and storage behaviour. Zero-width spaces are not separators.

    ArgumentTokenizer recognizes supported parameter prefixes without considering letter case at the start of the arguments or after these syntax separators, storing them under their canonical prefix. ParserUtil.verifyNoUnknownPrefixes uses the same boundary to reject unsupported parameter-like tokens of the reserved single-letter or addr/ form before values are parsed. For example, unsupported t/ produces a command-specific error. Longer slash-containing words such as wrong/value remain text.

    An extra slash marks literal parameter-like text, such as A//B or r//relay. Both prefix detection and unknown-prefix validation skip slash-terminated prefixes followed by another slash. After splitting arguments, the tokenizer strips surrounding whitespace and removes exactly one slash from a run of at least two slashes after a single-letter or addr token. Decoding happens once, including in the broad-search preamble, so decoded text cannot introduce new arguments. A///B becomes A//B, not A/B. URLs, network paths, quotation marks, and backslashes are not special syntax. Escaped tokens cannot supply required fields or bypass ordinary field validation.

    A slash-led value must be separated from its real prefix by whitespace: addr/ /home/coach supplies the address /home/coach, while addr//home/coach is literal text and does not introduce an address parameter.

    Commands that take no arguments (clear, help, and exit) reject extra text. remark requires exactly one r/ prefix. Index parsing scans ASCII digits once, capping the accumulated value at Integer.MAX_VALUE without building an arbitrary-precision number. It continues validating the remaining characters after reaching the cap, so an oversized number followed by text is still rejected. Leading zeroes are accepted; all-zero and malformed indexes are rejected. Oversized positive numbers reach the command's normal invalid-displayed-index check.

    Finding athletes

    TrackFlowParser dispatches find to FindCommandParser. The parser recognizes broad preamble keywords and n/, a/, p/, e/, addr/, r/, and t/ criteria. Broad keywords must precede the first field prefix. Unknown reserved prefixes, duplicate field prefixes, empty field values, and an empty search are rejected before the model is changed. ArgumentTokenizer decodes escaped prefix-like text once, before predicate construction.

    PersonContainsKeywordsPredicate combines the two groups as follows:

    • Broad keywords: any keyword may occur in any searchable field (OR).
    • Scoped fields: every supplied field must match its own value (AND). Each prefixed value is one phrase; find n/Avery Tan does not behave like the two broad keywords in find Avery Tan.
    • Both groups present: an athlete matches a broad keyword OR satisfies all supplied field criteria.
    • No criteria: matches no athletes. The nonempty-field guard prevents an empty allMatch from making a broad search match the entire roster.

    Matching is case-insensitive substring matching. Thus find n/avery a/Under 14 requires both the name and category, while find Blake n/avery a/Under 14 additionally includes athletes matching the broad keyword Blake. StringUtil.normalizeForCaseInsensitiveMatching supplies the comparison key for both search text and event identity, composing Unicode accents and applying the same case normalization. Broad and event-scoped searches therefore recognize equivalent spellings such as Greek Σ/ς and composed/decomposed É, including after saved-data reload. For n/ phrases, repeated ordinary spaces in both the stored name and query are collapsed for comparison only. Stored names, phrase order, partial matching, and other fields' internal-spacing semantics are preserved. find t/100m also matches an event such as 4x100m; exact-event matching is not implemented. Event names are joined with line breaks, which keeps ordinary single-line keywords from spanning two names.

    FindCommand replaces the active predicate through Model.updateFilteredPersonList. It searches the full roster, preserves the active sort, and starts displayed indexes at 1. Consecutive find commands do not narrow earlier results: put all required fields in one command. find and filter replace one another; list removes the filter. None of these view changes saves the roster.

    Design choices: broad OR matching helps when the relevant field is unknown; AND between named fields allows precise searches without adding another command. Substring matching supports partial names, contacts and events, with the tradeoff that short terms can produce extra matches. filter remains the exact age-category operation.

    Command autocomplete

    The command autocomplete feature is facilitated by CommandBox and AutocompleteEngine. It provides real-time dropdown suggestions for commands based on the user's input, and an intelligent prefix insertion mechanism to guide the user in completing complex commands.

    Implementation Details

    • AutocompleteEngine stores a predefined list of command templates (e.g., "add n/ a/ p/ e/ addr/", "edit INDEX n/ a/ p/ e/ addr/", "delete INDEX", "remark INDEX r/").
    • CommandBox listens to changes in the TextField's textProperty. While typing an initial command word, it queries AutocompleteEngine#getSuggestions for matching templates (matching case-insensitively) and displays them using a JavaFX Popup containing a ListView. Once whitespace or parameters are entered, or if there are no matches, the popup is hidden.
    • Selection: When the user selects a suggestion (via Mouse Click or Tab), CommandBox inserts the command word followed by a space (e.g., add ), positions the caret, and hides the popup. This leaves space for the user to insert an index or parameters if required.
    • Separation of Selection and Execution: Pressing Enter does not select or apply autocomplete suggestions. If the user presses Enter while the suggestion dropdown is visible, CommandBox hides the popup and executes the command as typed in the text field. This prevents accidental template insertions when a fast typist intends to submit their input.
    • Incremental Prefix Insertion: If the user presses Tab while the suggestion dropdown is closed (or after selecting a command), CommandBox uses AutocompleteEngine#getNextPrefix to scan the current input and append the next missing prefix based on the command's template. Existing prefixes are matched case-insensitively and regardless of order, allowing the user to construct the command sequentially by pressing Tab after entering each parameter's data. Prefix completion uses ArgumentTokenizer so escaped literal tokens do not count as supplied parameters.

    Design Considerations

    • Aspect: Suggestion selection key (Tab only vs Tab and Enter)
      • Alternative 1: Allow both Tab and Enter to select suggestions.
        • Pros: Familiar to users accustomed to web search bars that accept suggestions on Enter.
        • Cons: Interferes with command execution. A fast typist who types a command and presses Enter may accidentally apply an unwanted suggestion template instead of executing what they typed.
      • Alternative 2 (Current Choice): Use Tab exclusively to select suggestions and insert prefixes; reserve Enter strictly for command execution.
        • Pros: Follows established CLI and code-editor conventions (e.g., bash, zsh, IDE snippets) where Tab completes and Enter executes. Eliminates accidental command template overwrites upon submission.
        • Cons: Users who expect Enter to confirm a suggestion must use Tab or mouse click.
    • Aspect: Prefix insertion strategy
      • Alternative 1: Insert the entire command template at once (e.g., add n/ a/ p/ e/ addr/).
        • Pros: Shows the user all required fields immediately.
        • Cons: If the user accidentally executes the command before filling all fields, the parser fails with an invalid format error. It also requires manual navigation between the placeholders.
      • Alternative 2 (Current Choice): Incrementally insert prefixes using Tab.
        • Pros: Creates a guided, IDE-like snippet experience. Prevents trailing empty prefixes from causing parsing errors.
        • Cons: Requires slightly more complex logic to parse the current text and determine the next missing prefix.

    Athlete remarks

    RemarkCommandParser implements Parser<RemarkCommand> and reports invalid arguments with ParseException. It requires one r/ prefix and parses a positive, one-based index before creating the command. The command resolves that index against the displayed list during execution.

    RemarkCommand retains the new Remark and index, replaces the selected athlete with a copy, and restores the full roster view. An empty remark removes the note. If both the existing and replacement remarks are empty, the command throws CommandException before mutation, so the current view is retained and no save is attempted. It declares changesRoster() as true, so LogicManager uses the staged save-before-publication path. Success messages use the same athlete summary as add, edit, and delete, including age category, phone, and email. These diagrams omit helpers, the index field, and result internals.

    Event tagging

    Coaches record the track events each athlete competes in with tag INDEX t/EVENT... and remove them with untag INDEX t/EVENT.... Events are stored as the athlete's Tag set, so no change to Person or the JSON format was needed. Existing rosters should be backed up before upgrading. Older alphanumeric tags, including names longer than 30 characters, are preserved without truncation and remain removable with untag.

    Implementation details

    • TagCommandParser and UntagCommandParser extend EventTagCommandParser, which parses the shared INDEX t/EVENT [t/EVENT]... format. It rejects a missing or invalid index, a missing t/, and unknown prefixes. New events go through ParserUtil.parseTag, which trims them and reduces repeated inner whitespace to one space. Removal uses the same whitespace normalization but also accepts preserved legacy alphanumeric names.
    • TagCommand and UntagCommand extend EventTagCommand, which holds the index and events, looks up the target athlete in the displayed list, and replaces that athlete with a copy that has the updated events.
    • New Tag names are words of letters or digits separated by exactly one space or one hyphen (e.g. Long Jump, 110m-Hurdles, but not Long - Jump), up to 30 characters; MESSAGE_CONSTRAINTS states the same rule. Tag.fromStoredName also accepts the older unlimited alphanumeric format without truncation. JsonAdaptedTag uses it when loading, so a valid legacy event does not trigger recovery of the entire roster. Tag#equals and Tag#hashCode ignore case, so normal Set operations treat 100m and 100M as the same event while the first-entered spelling is kept for display.

    The class diagram below is a partial view of the event tagging classes. It shows how the two commands share parsing and execution steps; message constants, parser helpers such as ParserUtil, and the athlete's own event set are omitted.

    EventTagCommandParser implements Parser<T> with its own type parameter T. TagCommandParser and UntagCommandParser bind T to their command and implement getUsage() and createCommand(...), so the shared parse(...) method returns the correct command. Each command keeps the displayed-list Index and its non-empty set of events, but uses Model only while executing. EventTagCommand provides the shared steps: getTargetAthlete(...) finds the athlete at the index, and the static replaceEvents(...) creates and stores an updated copy of that athlete. TagCommand and UntagCommand differ only in how they work out the updated events.

    The shared parser's parseEvent(...) helper applies current constraints to new events. UntagCommandParser overrides it to recognize preserved legacy names too, allowing their removal while tag still rejects new names over 30 characters. These parsing helpers are omitted from the partial diagram.

    TagCommand adds only the events the athlete does not already have and lists any skipped events in its message. It fails only when every given event is already present, so that the coach knows nothing changed. UntagCommand fails without removing anything if any given event is not one of the athlete's events, as that usually signals a typo. Both commands then show the full roster, matching edit and remark.

    Design considerations

    • Aspect: How events are entered
      • Alternative 1 (current choice): Free text with light validation.
        • Pros: Supports any event, including unusual ones such as Javelin 500g, and avoids rejecting valid input.
        • Cons: The same event can be entered in different forms (e.g. 100m and 100 m).
      • Alternative 2: Choose from a fixed list of track events.
        • Pros: Consistent names across athletes.
        • Cons: Rejects events not on the list, which is overly strict for coaches whose events differ.
    • Aspect: Commands for changing events
      • Alternative 1 (current choice): Separate tag and untag commands that add to or remove from the existing events.
        • Pros: One event can be changed without retyping the others.
        • Cons: Two commands to learn.
      • Alternative 2: Replace all events through edit INDEX t/..., as in AB3.
        • Pros: One command.
        • Cons: Adding one event requires retyping every existing event, and a mistake silently removes events.

    Age-category filtering

    TrackFlowParser dispatches filter to FilterCommandParser. The parser requires exactly one case-insensitive a/ prefix and no preamble, rejects duplicates and unknown prefixes, and reuses ParserUtil.parseAgeCategory for the same canonical categories and normalization as add. Unsupported trailing text fails category validation.

    FilterCommand installs an AgeCategoryPredicate through Model.updateFilteredPersonList. The predicate compares Person.getAgeCategory() with the normalized category. Replacing the predicate searches the full underlying roster, retains the current displayed ordering, including any active sort, and does not mutate records. Feedback distinguishes zero, one, and multiple matches. The filter is a view state and is not persisted across restarts.

    The existing DeleteCommand resolves indexes against Model.getFilteredPersonList(), so it already targets the correct displayed athlete and keeps the predicate active. No delete implementation changes are needed for filtering. ListAthleteCommand restores PREDICATE_SHOW_ALL_PERSONS; find and filter replace one another.

    FilterCommandParserTest covers categories and invalid syntax, AgeCategoryPredicateTest covers exact category matching, and FilterCommandTest covers routing, feedback, unchanged records, replacing searches, invalid input, compatibility with existing deletion, and list restoration.

    Multi-field sorting

    TrackFlowParser dispatches sort to SortCommandParser. The parser requires one supported field and accepts one optional order, defaulting to ascending. It accepts short (asc, desc) and long (ascending, descending) order names without considering letter case, while rejecting missing fields, unsupported values, and extra arguments.

    ModelManager wraps its existing FilteredList<Person> in a SortedList<Person>. SortCommand installs the selected comparator through Model.updateSortedPersonList, changing only the displayed view rather than the underlying roster order. Sorting composes with find and filter, and indexed commands continue to resolve athletes against exactly what the user sees. ListAthleteCommand clears both the filter and comparator, restoring the full roster in saved order. Sorting and filtering are session-only view changes and are not persisted.

    Text fields are compared without considering letter case. Name comparison also collapses repeated ordinary spaces in the comparison key without rewriting the displayed or saved name. Phone sorting converts Phone.getSignificantDigits() to an arbitrary-precision numeric value. The shared key includes a bracketed country code such as (+65) and excludes other bracketed notes, including digits in (5) or (Office 9). Displayed and saved text is unchanged, and large numeric values do not overflow. Duplicate identity uses the same significant digits key, so note digits are ignored there too. Age categories use the competition order Under 14, Under 16, Under 18, Under 20, Open.

    Appendix: Requirements

    Product scope

    Target user profile:

    • High-school or club track-and-field coaches who manage large student-athlete rosters.
    • Coaches who need to maintain athletes' contact details and age categories on their own computer.
    • Keyboard-proficient users who type quickly, prefer typing to mouse interactions, and are comfortable learning short text commands.
    • Individual users who need a desktop application that works without an account or internet connection.

    Value proposition: TrackFlow helps a coach maintain and retrieve an organized athlete roster through short keyboard commands, reducing the effort of navigating forms and keeping contact information available between training sessions.

    v1.5 scope: The release supports adding, listing, editing, remarking, searching, filtering, sorting, tagging and untagging events, deleting, clearing, built-in help, and exit. New athletes require a name, age category, phone number, email address, and nonblank address. Remarks can be added or removed separately. Roster changes are saved locally before being published to the live model; view-only commands do not save roster data.

    Future features are marked [Future] below. Cloud synchronization and collaborative editing are excluded from this single-user, local product. Athletes are records, not application users.

    Persistence and recovery status

    ApplicationHome resolves the real location of the code archive. For a packaged JAR, its parent directory is home, including when launched through a symbolic link or from another working directory. An IDE/test launch from unpacked class files uses the process working directory. Resolution does not log because LogsCenter needs the same home before normal application startup. An unresolvable code location stops initialization instead of silently choosing another folder.

    MainApp loads data/trackflow.json inside that home. If no file exists, it supplies the sample roster; the first successful roster change creates the file. An intentionally saved empty roster remains empty on restart. preferences.json and rotated logs share the same home. Backups and temporary roster saves use roster-file siblings.

    JsonUserPrefsStorage rejects null GUI settings and dimensions that are nonpositive or nonfinite, including values Jackson assigns directly to fields. Missing properties retain their defaults. Coordinates may be null (automatic placement) or integer positions; the UI handles actual screen visibility. MainApp.initPrefs recovers from invalid preferences with defaults and attempts to save them without changing the roster.

    JsonUtil requires exactly one JSON root followed only by whitespace, for both rosters and preferences. Extra roots, garbage and truncation cause a loading error; reading never silently accepts just the first root. JsonRosterStorage converts malformed JSON, repeated keys, null roots, missing or null persons lists, null athletes, null tag entries, invalid saved field values, and duplicate athletes into DataLoadingException. A leading UTF-8 byte order mark is tolerated, and an athlete whose address or remark is absent loads with an empty value rather than failing the whole file. When loading fails, MainApp preserves the original bytes in a sibling file named trackflow.json.unreadable-<UUID>.bak, logs its path, shows the path in the result display at start-up, and starts an empty roster. Each failed load creates a separate backup without overwriting earlier backups. Subsequent successful roster changes can replace the active file while the backup remains available for manual recovery. If backup creation fails, startup stops before commands become available, protecting the original from being overwritten.

    Use cases

    For every use case below, the system is TrackFlow and the primary actor is the coach. MSS means main success scenario. UC01–UC07 describe implemented workflows. Future requirements remain in the user stories.

    UC01: Register an athlete

    Related stories: US01, US02, US05, US06, US07.
    Precondition: TrackFlow is open.
    Success postcondition: One complete athlete record is saved and displayed in the roster.

    MSS

    1. The coach requests to view the roster.
    2. TrackFlow displays the roster with current indexes, or indicates that it is empty.
    3. The coach submits the new athlete's name, age category, phone number, email address, and address.
    4. TrackFlow validates the input, checks for a duplicate, and saves the new record.
    5. TrackFlow displays the full roster in the current sort order, or saved roster order if no sort is active, and displays the added athlete's details.

    Use case ends.

    Extensions

    • 3a. A required field is missing, repeated, or invalid, or an unsupported parameter is supplied.
      • 3a1. TrackFlow shows the applicable error and retains the entered command for correction. The roster is unchanged.
      • Use case resumes at step 3.
    • 4a. The normalized name and either phone or email match an existing athlete.
      • 4a1. TrackFlow reports the duplicate and leaves the roster unchanged. Age category does not affect this check. A shared name alone is allowed.
      • Use case resumes at step 3.
    • 4b. The change cannot be saved.
      • 4b1. TrackFlow reports the save failure. No athlete is added, and the previous roster remains visible.
      • Use case ends.
    • 4c. A differently named athlete shares the phone or email.
      • 4c1. TrackFlow saves the new record and includes a possible-duplicate warning listing each matching athlete's name, age category, phone, email, and the matching contact field(s). Hidden athletes are included without using displayed indexes.
      • Use case resumes at step 5.

    UC02: Remove an athlete

    Related stories: US02, US03, US05, US07.
    Precondition: TrackFlow is open.
    Success postcondition: Exactly the selected athlete is permanently removed from the saved roster.

    MSS

    1. The coach requests to list athletes.
    2. TrackFlow displays the roster in the current displayed ordering with current indexes.
    3. The coach checks the athlete's details and requests deletion using the athlete's displayed index.
    4. TrackFlow saves the deletion, refreshes and renumbers the roster, and displays the deleted athlete's details.

    Use case ends. Deletion has no confirmation prompt, archive, or undo operation.

    Extensions

    • 2a. The roster is empty.
      • 2a1. TrackFlow reports that the roster is empty.
      • Use case ends.
    • 3a. The index is missing, malformed, or does not identify an athlete in the current list, or extra arguments are supplied.
      • 3a1. TrackFlow explains the error and leaves the roster unchanged.
      • Use case resumes at step 3.
    • 4a. The deletion cannot be saved.
      • 4a1. TrackFlow reports the failure and retains the athlete in the roster.
      • Use case ends.

    UC03: Edit an athlete's details

    Related stories: US02, US05, US06, US07, US09.
    Precondition: TrackFlow is open and the athlete is in the roster.
    Success postcondition: The selected athlete's updated details are saved; omitted fields, remarks, and events are retained.

    MSS

    1. The coach views the roster, optionally using find, filter, or sort.
    2. TrackFlow displays the matching athletes with current indexes and ordering.
    3. The coach submits edit INDEX with at least one supported field to change.
    4. TrackFlow resolves the displayed index, validates the proposed record, and checks the full roster for duplicates.
    5. TrackFlow saves the change, displays the full roster with the active sort retained, and confirms the edit.

    Use case ends.

    Extensions

    • 3a. The index or field values are missing, invalid, repeated, or unsupported.
      • 3a1. TrackFlow reports the error and leaves the roster and display unchanged.
      • Use case resumes at step 3.
    • 3b. All supplied values are the same as the athlete's stored details.
      • 3b1. TrackFlow reports that at least one field must differ, without saving or changing the view. A change to the stored phone formatting or note is treated as an edit.
      • Use case resumes at step 3.
    • 4a. The edit would duplicate another athlete, including one hidden by the current filter.
      • 4a1. TrackFlow rejects the edit and leaves the roster unchanged.
      • Use case resumes at step 3.
    • 5a. Saving fails.
      • 5a1. TrackFlow reports the failure and retains the previous roster, filter, and sort order.
      • Use case ends.

    UC04: Continue working with a saved roster

    Related stories: US04, US07, US08.
    Precondition: A saved roster exists, or this is the first launch.
    Success postcondition: On reopening, the coach sees the saved roster, including successful additions, edits, remark updates, deletions, and clearing.

    MSS

    1. The coach closes TrackFlow.
    2. The coach launches TrackFlow again.
    3. TrackFlow loads the saved roster into the displayed list.
    4. The coach requests to list athletes.
    5. TrackFlow displays the saved athletes with their current indexes.

    Use case ends.

    Extensions

    • 3a. No saved roster exists, as on first use.
      • 3a1. TrackFlow starts with sample athletes and logs that no saved roster was found. The data file is created after the first successful roster change.
      • Use case resumes at step 4.
    • 3b. The saved roster cannot be loaded.
      • 3b1. TrackFlow logs the loading failure and backup path, and starts with an empty roster while preserving the unrecovered data in a separate file.
      • 3b2. Subsequent successful changes create a new active roster without replacing the preserved data. TrackFlow does not claim the old records were restored; the preserved copy remains until the coach removes it outside TrackFlow.
      • Use case resumes at step 4.
    • 3c. The saved roster cannot be loaded and its backup cannot be created.
      • 3c1. TrackFlow stops startup before accepting commands to protect the original file.
      • Use case ends.

    UC05: Filter athletes by age category

    Status: Implemented in v1.4.

    Precondition: TrackFlow is open.
    Success postcondition: Only matching athletes are displayed; stored records are unchanged.

    MSS

    2. TrackFlow searches the full roster and displays matching athletes in the current displayed ordering, including any active sort, with current indexes and the match count.
    3. The coach enters list to restore the complete roster, or uses the displayed indexes with existing commands.

    UC06: Replace or remove an athlete remark

    Related stories: US05, US07.
    Precondition: TrackFlow displays the athlete to update.
    Success postcondition: The replacement remark, or its removal, is saved without changing other stored fields.

    MSS

    1. The coach submits remark INDEX r/REMARK using the current displayed index.
    2. TrackFlow replaces the existing remark; an empty value removes it.
    3. TrackFlow saves the change, restores the full roster with the active sort retained, and confirms the update.

    Extensions

    • 2a. The coach requests removal when the athlete has no remark. TrackFlow reports that no remark can be removed, retaining the current roster and view without saving.

    UC07: Add or remove an athlete's track events

    Related stories: US05, US07, US12.
    Precondition: TrackFlow displays the athlete to update.
    Success postcondition: The athlete's events are updated and saved without changing other stored fields.

    MSS

    1. The coach submits tag INDEX t/EVENT [t/EVENT]... using the current displayed index.
    2. TrackFlow adds the events the athlete does not already have.
    3. TrackFlow saves the change, shows the full roster, and confirms which events were added.

    Use case ends.

    Extensions

    • 1a. The index is invalid, no t/ is given, or an event is invalid. TrackFlow reports the error and leaves the roster unchanged.
    • 2a. The athlete already has some of the events. TrackFlow adds the rest and also lists the skipped events.
    • 2b. The athlete already has all of the events. TrackFlow reports this and leaves the roster unchanged.
    • 3a. Saving fails. TrackFlow reports the failure and leaves the live roster unchanged.

    Removing events with untag INDEX t/EVENT [t/EVENT]... follows the same steps, except that if any event is not one of the athlete's events, TrackFlow reports it and removes nothing.

    Glossary

    Term Definition
    Active roster The athlete records currently maintained and displayed by the coach, excluding any separately preserved unrecovered data and, if archiving is introduced, archived records.
    Age category A coach-assigned competition grouping: Under 14, Under 16, Under 18, Under 20, or Open. TrackFlow stores the category, not an exact age or date of birth, and does not verify competition eligibility.
    Athlete A student-athlete whose contact and age-category information is recorded in TrackFlow. An athlete does not log in to the application.
    Archive / restore A future capability to remove a record from the active roster while retaining it, and later return it to the active roster. This differs from permanent deletion.
    CLI / GUI Command-line interface / graphical user interface. TrackFlow accepts typed commands in a graphical window and uses that window to display records and feedback.
    Displayed index An athlete's positive, one-based position in the current displayed list. It is not a permanent identifier and may change after roster updates.
    Duplicate athlete record A record with the same normalized name and either the same phone or email as another record, regardless of age category. Differently named records sharing contacts are allowed with a possible-duplicate warning on add or edit.
    Eligibility Whether an athlete meets the recorded participation conditions for a competition or event. Eligibility logs are a future feature, distinct from assigning an age category.
    Event specialization An athletics discipline, such as sprinting or long jump, associated with an athlete through the tag and untag commands.
    Guardian A parent or other responsible adult whose future contact record may be linked to one or more athletes.
    Local persistence Automatically saving roster changes on the coach's computer and loading them in a later application session.
    Implemented A feature available in the current v1.5 code. Future features are identified separately.
    Normalized field A value prepared for comparison: surrounding whitespace is removed; name and age-category internal spaces are collapsed; name, category, and email comparisons ignore letter case; phone comparisons ignore permitted formatting characters and use the digits. Display formatting may be retained.
    Participation log A future record of an athlete's involvement in training or competition.
    Relay squad / event group A future grouping of athletes for a relay team or a particular athletics event.
    Unrecovered data Previously saved roster data that TrackFlow could not load, preserved in a separate .bak file before starting an empty roster. If preservation fails, startup stops.

    Duplicate identity and complete equality

    Duplicate checks use normalized name plus either matching significant phone digits or matching email, regardless of age category. Bracketed notes are ignored; a country code such as (+65) counts as part of the phone number. Name normalization ignores case and repeated spaces; email matching ignores case. Complete equality applies each field's equality rules across every field, including category, address, remark, and events. Phone formatting and event-name case do not by themselves make records unequal. These are separate contracts.

    1. Start with only Avery: run clear, then add n/Avery Tan a/Under 14 p/91234567 e/avery@example.com addr/Home. Attempt to add AVERY TAN with the same phone and a different email and category. Expect a duplicate error, with no saved changes. Repeat with a different phone and matching email (including different email case); expect rejection again.
    2. Add a record with the same name but both a different phone and a different email. Expect success.
    3. Add Jordan Lee with Avery's phone and a different email. Expect success with a possible-duplicate warning listing Avery's name, category, phone and email, with Matches: phone. Edit Jordan to a different phone and Avery's email in different case; expect Matches: email. Match both contacts and expect one Avery entry with Matches: phone and email. Different names sharing contact details are permitted.
    4. Run find n/Jordan, then attempt to add Avery's duplicate. Expect rejection even though Avery is hidden.
    5. With Jordan displayed, attempt to edit the name to AVERY TAN while retaining Avery's phone. Expect rejection because duplicate checks search the complete roster. The previous filter and roster remain unchanged.
    6. Restart and repeat the duplicate attempts. Expect the same decisions after reloading.
    7. In a separate empty disposable roster, add two Alex Tan records with different phones and emails. Hide both using find n/Nobody, then add Blake Tan with the first Alex's phone and the second Alex's email. Expect two separate warning entries identifying each Alex's contact details, with Matches: phone and Matches: email respectively. Repeat after a restart and an edit while only Blake is displayed. The warning must not borrow indexes from the filtered list or include Blake as their own match. Developer-only check: the automated PersonTest and DuplicatePersistenceTest checks in the testing guide verify complete equality separately from duplicate identity. Address-only and remark-only changes affect full equality without changing duplicate identity.
