    Testing guide

    Running tests

    Use the Zulu JDK 25 setup for both IntelliJ and Gradle. You can run tests in two ways.

    • Method 1: Using IntelliJ JUnit test runner
      • To run all tests, right-click on the src/test/java folder and choose Run 'All Tests'
      • To run a subset of tests, you can right-click on a test package, test class, or a test and choose the corresponding run action (for example, Run 'PersonTest')
    • Method 2: Using Gradle
      • Open a console and run the command gradlew clean test (Mac/Linux: ./gradlew clean test)

    Link: Read this Gradle Tutorial from the se-edu/guides to learn more about using Gradle.

    Types of tests

    This project has three types of tests:

    1. Unit tests target the lowest-level methods and classes.
      For example: trackflow.commons.util.StringUtilTest
    2. Integration tests check how multiple code units work together; the individual units are assumed to work.
      For example: trackflow.storage.StorageManagerTest
    3. Hybrid tests combine unit and integration testing. These tests check both the individual units and how they work together.
      For example: trackflow.logic.LogicManagerTest

    Reading and reviewing tests

    Test names describe the operation, scenario and expected outcome. Read the fixture setup first: each @BeforeEach or @TempDir establishes the starting roster and isolates saved files from a real installation. An assertion on the displayed list checks the view; it does not by itself establish that the complete roster or saved JSON is correct.

    Area Useful starting points What the checks establish
    Command syntax and escaping TrackFlowParserTest, ArgumentTokenizerTest, ParserRobustnessTest Accepted/rejected input, one-time slash decoding, and unchanged state after rejection
    Search and indexed commands PersonContainsKeywordsPredicateTest, FilterCommandTest, SortCommandTest Broad OR versus scoped AND, replacement of filters, and indexes in the displayed order
    Identity and saved records PersonTest, DuplicatePersistenceTest, JsonSerializableRosterTest Duplicate identity, complete equality, and decisions after reloading
    Save failures and startup LogicManagerTest, MainAppTest, StartupProcessTest Publication only after saving, preservation of unreadable data, and application-home paths
    Screen placement WindowPlacementTest Bounds calculations for screens and saved preferences; actual rendering still needs manual checks

    For failure tests, check the expected exception or feedback as well as the unchanged roster, view and saved file. For persistence tests, look for a fresh storage read or model reconstruction rather than an assertion against only the original in-memory object. Comments explain unusual inputs, isolation decisions and regression risks; ordinary setup and self-explanatory assertions do not need a comment on every line.

    The automated suite does not drive the complete JavaFX interface. Follow the DG's manual testing appendix on the final packaged JAR for keyboard behaviour, rendering, scrolling, screen scaling and platform/runtime compatibility. Record the exact build and environment tested; passing helper tests alone is not evidence of those UI properties.

    Build and focused tests

    Run ./gradlew clean check coverage shadowJar to build build/libs/TrackFlow.jar, run the automated tests, and check Java style. On Windows, use gradlew.bat in place of ./gradlew.

    For focused duplicate/equality checks, run:

    ./gradlew test --tests trackflow.model.person.PersonTest --tests trackflow.logic.DuplicatePersistenceTest

    For parser boundaries, double-slash escapes, literal paths, empty values, duplicate parameters, null inputs, multiline input, large indexes, and rejected-command checks, run:

    ./gradlew test \
    --tests trackflow.logic.ParserRobustnessTest \
    --tests trackflow.logic.parser.ArgumentTokenizerTest \
    --tests trackflow.logic.parser.ParserUtilTest \
    --tests trackflow.logic.parser.TrackFlowParserTest

    ParserRobustnessTest uses real JSON storage in a temporary folder to check that parsed values survive reload and that invalid commands preserve the roster, current predicate/comparator, displayed athletes, and saved file. The tests distinguish Java null API inputs from the literal text null, exercise duplicate parameters even when one value is empty or escaped, and verify that restarts and unrelated edits do not decode stored text again. The tokenizer tests cover every single-letter escape in both cases, multiple whitespace boundaries, long slash runs, URLs, network paths, and ordinary quotes/backslashes. Parser tests check all 120 orders of the five add fields. Existing JsonRosterStorageTest and MainAppTest also check null JSON roots/entries and preservation of malformed data.

    For startup/preferences, strict JSON roots, application-home paths and unavailable file logging, run:

    ./gradlew test \
    --tests trackflow.MainAppTest \
    --tests trackflow.storage.JsonUserPrefsStorageTest \
    --tests trackflow.commons.core.GuiSettingsTest \
    --tests trackflow.commons.util.JsonUtilTest \
    --tests trackflow.commons.util.ApplicationHomeTest \
    --tests trackflow.StartupProcessTest

    StartupProcessTest packages the compiled application classes into a temporary JAR and starts bounded child JVMs with the normal test runtime dependencies. It checks recovery, saving and reopening from another directory, a home path containing spaces and %u, temporary-file cleanup, and console fallback when the log path is blocked. It initializes the application and runs real commands/storage without opening a GUI; it does not replace native window tests or launch verification of the final release JAR on each supported runtime/platform.

    Automated results are in build/reports/tests/test/index.html; Checkstyle reports are in build/reports/checkstyle/. Verify guide examples and startup behavior using the manual testing procedures.
