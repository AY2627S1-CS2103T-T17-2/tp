    Setting up and getting started

    Runtime and build requirements

    Use Azul Zulu JDK 25 for development and release verification. Configure JAVA_HOME, the IntelliJ project SDK, and the Gradle JVM to point to that installation. Confirm java -version and ./gradlew --version both use Java 25 before building. Do not use JDK 17 or assume a later major Java version has been tested.

    On macOS, select the JDK FX distribution, which includes JavaFX, and match the runtime to your processor (Apple Silicon or Intel). Java CI requests Zulu 25 with java-package: jdk+fx. The build also bundles JavaFX 17.0.7 for Windows, Linux, and Intel macOS. It does not declare a separate Apple Silicon JavaFX dependency, so the packaged JAR must be checked with the prescribed runtime on each supported architecture before release. A successful unit test run does not establish GUI runtime compatibility.

    Setting up the project on your computer

    Caution: Follow the steps below precisely. The setup may fail if you skip or change a step.

    First, fork this repo, and clone the fork into your computer.

    If you plan to use IntelliJ IDEA (highly recommended):

    1. Configure the JDK: Follow the guide [se-edu/guides] IDEA: Configuring the JDK to configure both the project SDK and Gradle JVM to use Azul Zulu JDK 25 (JDK FX on macOS).
    2. Import the project as a Gradle project: Follow the guide [se-edu/guides] IDEA: Importing a Gradle project to import the project into IDEA.
      Note: Importing a Gradle project is slightly different from importing a normal Java project.
    3. Verify the setup:
      1. Run trackflow.Main and try a few commands.
      2. Run the tests to ensure they all pass.

    Before writing code

    1. Configure the coding style

      Follow the SE-EDU Java coding standard (Basic + Intermediate). The repository's config/checkstyle/checkstyle.xml checks a subset of these rules; review comments for accuracy as well as checking their format.

      If using IDEA, follow the guide [se-edu/guides] IDEA: Configuring the code style to set up IDEA's coding style to match ours.

      Tip: Optionally, follow the guide [se-edu/guides] Using Checkstyle to learn how to use Checkstyle in IDEA, for example to report problems as you write code.

    2. Set up CI

      This project includes GitHub Actions configuration files in .github/workflows. Java CI is configured for pushes and pull requests; MarkBind deployment is configured for pushes to master. Check the Actions page for a run against the exact release commit. Configuration alone does not confirm that a run occurred.

    3. Learn the design

      When you are ready to start coding, we recommend that you get some sense of the overall design by reading about TrackFlow’s architecture.

    4. Read the tutorials These upstream tutorials explain the original project. Their class names and paths may differ from TrackFlow; use trackflow.Main, TrackFlowParser, AthleteRoster, and JsonRosterStorage in this repository.

    Documenting code changes

    Write descriptive Javadoc headers for classes, public constructors, and public methods. Simple getters/setters, test code, and overrides whose inherited documentation applies exactly may omit a header. An override with a different contract should explain it, using {@inheritDoc} where helpful.

    Start method summaries with a verb such as "Returns", "Creates", or "Updates". Explain behavior callers need to know: accepted values, normalization, empty or null handling, side effects, returned views or copies, and failures. Keep comments consistent with the implementation; do not promise validation, persistence, or features that the method does not provide. Use English with American spelling.

    Use @param for every parameter or omit the tags when the description already explains all parameters. Include useful @return and @throws descriptions. Keep the opening /** on its own line, separate the summary from block tags with a blank line, and end tag descriptions with punctuation. Link related API types with {@link ...} so generated documentation can resolve them.

    Run the following from the repository root before opening a documentation PR:

    ./gradlew check javadoc

    On Windows, use gradlew.bat. Open build/docs/javadoc/index.html to inspect the generated API documentation. The Javadoc tool can also report optional missing tags or comments on simple accessors/constants; those warnings are separate from the course standard's documented exceptions. Resolve malformed markup and broken references, and manually verify that each changed header describes the current behavior.

    Checkstyle enforces only part of the standard. During review, also check comment accuracy, athlete-facing vocabulary, American spelling in Java comments, verb-based method names, and wrapped-line indentation (8 spaces beyond the original line). Preserve documented storage keys when changing human-readable wording.
